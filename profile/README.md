<p>先看短会话场景。特征是每次用几分钟、用完就断、不要求身份连续。这类场景对粘性没要求，甚至可以按请求轮换，重点在命中率和失败率。池子大、地区覆盖广的方案更合适。</p>

<p>短会话的成本敏感度高，因为请求多、单次价值低。按请求计费或按流量计费的模型更划算，按地址计费会显得贵。选型时先算清每月请求量。</p>

<p>再看批量查询场景。特征是一次发很多请求、彼此独立、要求分散度高。这类场景要的是并发能力和池子的承载，粘性反而不重要，甚至可以主动要求轮换。</p>

<p>批量场景的关键指标是峰值承载和失败重试成本。池子再大，同时打满也会互相拖累，表现为延迟整体抬升、成功率下滑。签合同前问清峰值限速规则。</p>

<p>最后看连续登录场景。特征是会话长、要求身份连续。这类场景必须选会话保持，而且粘性时长要大于业务会话。规则不匹配的方案，再便宜也不能用。</p>

<p>三种用途对应三套判断标准。推荐的时候把场景说清楚，对方才能对号入座；只给一个名字，等于把选择成本转嫁给了用户。</p>

<p>还有一类边界场景值得单说：短会话但要求同一地区。这类需求对命中率和粘性的要求同时存在，往往要选支持地区锁定的方案，价格会高一档。</p>
